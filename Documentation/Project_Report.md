# SEIM Project Report

## Executive Summary

SEIM is a Unity-based earthquake simulation and virtual sensing prototype integrated with a separate backend at `D:\Projects\SEIM-Backend`. Its central achievement is an end-to-end path from a simulated earthquake to generated sensor telemetry, independent station-level phase detection, epicenter estimation, MQTT transport, Kafka streaming, and PostgreSQL persistence. The Unity project also includes an event lifecycle with a conditional tsunami state and a building-response component.

The project is best described as a physics-informed simulation and integration prototype, not yet as a complete multi-hazard monitoring platform or a deployed early-warning system. The earthquake model and the sensing path are implemented, but several stated objectives are not present in the current code: performance-based hardware sizing, an ML severity model and its training pipeline, and active simulation feeds for ocean-bottom pressure, DART, and tide-gauge sensors. The project contains a real MQTT integration contract; unchanged operation with replacement physical sensors is a plausible design goal, but is not demonstrated by the Unity repository alone.

## What the Project Does

### 1. Owns an earthquake event lifecycle

`SimManager` stores the current event state and its authoritative parameters: magnitude, surface epicenter, depth, offshore status, and elapsed simulation time. It transitions through `Idle`, `EarthquakeActive`, `TsunamiActive`, and `Ended`. An offshore event meeting the configured magnitude and depth thresholds schedules a transition to `TsunamiActive` after a delay. This is a lifecycle trigger; it is not, by itself, a physical tsunami propagation model.

### 2. Generates earthquake shaking from a shared model

`EarthquakeModel` is a stateless utility that reads event parameters from `SimManager` and computes a three-axis seismic reading at a requested position and time. It includes hypocentral distance, independent P- and S-wave speeds, a Boore-Atkinson-style ground-motion prediction equation (GMPE), site-class amplification, wave arrival timing, and a simplified waveform envelope.

The live seismic station feeder calls this model at a configurable sample interval and records the resulting readings. `BuildingShaker` also calls the same model, so the virtual station acceleration and building response share the same underlying event and shaking calculation. This common source of simulated shaking is a meaningful architectural strength. It does not mean every modality has a single, complete physical model: GNSS displacement is separately generated by a simplified ramp-and-hold approximation scaled from GMPE PGA.

### 3. Processes raw station samples into detections

`SensorDataStore` keeps the latest readings and a bounded history of seismic samples. Each seismic reading is passed to `EpicenterProcessorNode`, which maintains a separate `PWaveDetector` for each station. The detector applies STA/LTA thresholds to the raw acceleration magnitude to identify a first P-wave trigger and a later, stronger S-wave trigger. It also exposes an S-P interval as a distance cross-check.

After the configured minimum number of stations have independently triggered, `EpicenterProcessorNode` uses their station positions and P-wave arrival times to estimate a two-dimensional surface epicenter. `Trilateration` implements an iterative Gauss-Newton least-squares solver. The result and contributing station IDs are serialized as a detection event and published to MQTT when a publisher is present.

### 4. Publishes simulation output over MQTT

`MqttPublisher` publishes JSON payloads using QoS 0 (at-most-once delivery). Sensor readings use the topic convention `sensors/{ReadingType}/readings`; epicenter detections use `detections/Epicenter/events`. The publisher makes a connection attempt on startup and attempts reconnection around publication if disconnected. If the broker remains unavailable, a reading can be dropped while the local simulation continues.

### 5. Ingests telemetry through the backend

The backend is maintained separately at `D:\Projects\SEIM-Backend`. Its MQTT bridge subscribes to `sensors/+/readings` and `detections/+/events`. For raw sensor JSON, it derives `readingType` from the topic, reads the station ID and timestamp from the payload, assigns an event UUID, and wraps the raw payload in a Kafka envelope. Detection JSON is similarly assigned a detection type from the topic and wrapped for Kafka; a valid event UUID from Unity is retained.

The backend publishes sensor envelopes to Kafka topic `sensor.readings` and detection envelopes to `detected.events`. Kafka consumers pass these envelopes to services that persist sensor readings in `sensor_readings` and normalized epicenter detections in `detected_events`. Sensor payloads are stored as JSONB; event IDs have unique constraints and duplicate checks. A direct `POST /api/sensor-readings` path is available for ingestion tests that bypass MQTT and Kafka.

Sensor persistence is downsampled by default: the backend stores at most one reading per reading type and station per configured interval, currently 1000 ms. It can therefore ingest high-rate telemetry without persisting every sample. The interval is based on backend receive time, not the sensor timestamp. Detection events use their separate path and are not subject to this sensor-reading downsampler.

### 6. Supports local telemetry export

`SensorDataStore` can optionally append recorded readings as JSON Lines under the project `data` directory. This provides a local replay or analysis artifact when enabled. The setting is off by default. Exporting telemetry does not automatically create a labeled dataset, train an ML model, or calculate severity.

## Technology Stack

### Unity simulation and sensing

- **Unity 6.2 (`6000.2.5f1`)** is the simulation runtime and editor.
- **C# 9** scripts target **.NET Standard 2.1** in the generated Unity project files.
- **Unity Test Framework 1.5.1** is included for Unity-side tests. The repository also has editor-invoked test scripts for specific simulation and sensing behaviors.
- **M2Mqtt** is included in the Unity project and used by `MqttPublisher` to connect to the broker.
- **Unity `JsonUtility` and JSON Lines** are used to serialize sensor payloads and optionally export local readings.
- **Unity Input System and URP** are among the project packages; they support the application/runtime, while the earthquake calculation and sensing path are implemented in project C# scripts.

### Documented integration backend

The Unity project is in `D:\Projects\SEIM`; the connected backend implementation is in `D:\Projects\SEIM-Backend`.

- **Unity side:** Unity 6.2 (`6000.2.5f1`), C# 9, .NET Standard 2.1, M2Mqtt, `JsonUtility`, and optional JSON Lines telemetry export.
- **Backend service:** Java 21, Spring Boot 4.1.1, Maven, Eclipse Paho MQTT client 1.2.5, Spring Kafka, Spring Data JPA/Hibernate, Jackson, and PostgreSQL JDBC.
- **Infrastructure:** Eclipse Mosquitto 2, Apache Kafka 3.8.0 in single-node KRaft mode, PostgreSQL 16, and Docker Compose. The backend app is containerized with Eclipse Temurin 21.
- **Backend test dependencies:** Spring Boot Kafka/Web MVC/validation test starters and H2 are declared in Maven; this report does not claim those tests were run as part of the report update.
- **Unity packages:** Unity Test Framework 1.5.1, Input System, and URP are included; they support the Unity application and its local tests rather than the backend pipeline.

The inspected backend code implements the documented bridge, producers, consumers, storage services, database entities, configuration, and Docker Compose topology. This confirms code-level integration, but does not by itself prove that the stack is currently running or that a live message was observed during this report update.

### Data and interface formats

Sensor and detection payloads are JSON. Sensor topics follow `sensors/{ReadingType}/readings`; detection events use `detections/Epicenter/events`. Optional local telemetry export uses newline-delimited JSON. MQTT currently uses QoS 0, and the project does not include a schema registry or guaranteed-delivery queue in the Unity client.

The Layer 2 plan describes a rudimentary, explicitly scoped tsunami simulation. Its objectives and current evidence are:

The thresholds are configurable. This determines eligibility and simulation state; it does not model a tsunami wave. |
| Propagate waves using shallow-water speed, with deep and coastal depth assumptions | **Planned, not implemented** | `Documentation/layer2.md` proposes `c = sqrt(g * depth)` with simplified deep-ocean and coastal depth zones. No `TsunamiModel` or corresponding implementation was found. |

The planned full test that verifies non-zero DART/tide-gauge readings cannot pass until the model and feeder are implemented. |

The project therefore achieves a configurable tsunami-trigger decision, not tsunami detection, propagation, forecasting, or coastal inundation modeling. The plan deliberately describes a first-pass model rather than a bathymetry-resolved forecast system; even that first-pass propagation and sensor-output work remains future implementation.

## What the Project Achieves

- Establishes a single authoritative earthquake event state and parameter source for the Unity simulation.
- Produces time-varying, distance-sensitive seismic readings with 3-axis output and distinct P/S arrival behavior.
- Connects generated samples to per-station STA/LTA detection rather than assigning arrival times directly to sensors.
- Estimates a surface epicenter from independently detected P-wave arrival times at multiple stations.
- Publishes raw readings and derived epicenter events over a documented MQTT topic contract.
- Connects Unity MQTT messages to the backend's Kafka topics and PostgreSQL persistence path, with optional local JSONL export.
- Includes core algorithm and integration-oriented test scripts for the earthquake model, event lifecycle, station feeders, trilateration, and the sensor pipeline.

Taken together, this is a useful prototype for exercising how simulated ground motion can flow through a virtual sensing and event-ingestion pipeline. It also offers an experimental base for measuring detection latency and localization error under controlled event parameters. That measurement capability is a prerequisite for performance-based network sizing, but the sizing optimization itself remains future work.

## Important Technical Limits

1. **The physics are simplified.** The GMPE is described in code as Boore-Atkinson-style and uses project-specific constants. It is not presented as a validated regional ground-motion model. Waveform shape, site amplification, and GNSS displacement are approximations.
2. **Localization is two-dimensional.** The solver estimates a surface `(x, z)` epicenter from arrival times. It does not jointly estimate depth or magnitude. The implementation assumes the supplied station coordinates, speed conversion, and timing are consistent.
3. **STA/LTA phase classification is simplified.** The first threshold crossing is treated as P and a later, stronger crossing as S. This is not a full seismic phase classifier using polarization, noise characterization, or real sensor calibration.
4. **Tsunami behavior is incomplete.** The manager can enter a tsunami state based on event thresholds, but this workspace contains no `TsunamiModel` or `StationTsunamiFeeder`; DART and tide-gauge signal generation is therefore not demonstrated.
5. **Transport and persistence are not lossless.** Unity MQTT publication uses QoS 0 and can drop data if connection/retry fails. The backend's sensor downsampler intentionally discards readings inside its configured per-station interval. Its README also documents no MQTT authentication, a single Kafka broker, no dead-letter queue, and consumer failures that are logged and skipped.
6. **No production or operational claim is supported.** The code and docs show a prototype with tests and manual verification guidance, not field deployment, measured operational reliability, or validated warning performance.

## Validation Present in the Project

The repository contains scripts intended to check core behavior:

- `TrilaterationTest` synthesizes station arrival times and evaluates epicenter estimation.
- `EarthquakeModelPhase2Test` checks that more distant stations have later arrivals and lower peak acceleration.
- `SimManagerPhase1Test` checks event-state changes and the offshore tsunami-trigger condition.
- `StationFeedersPhase3Test` exercises feeder integration.
- `DumbSensorPipelineTest` exercises the sensor-to-detection path with controlled readings.
- The Unity and backend READMEs document manual MQTT, Kafka, and PostgreSQL verification steps; the backend also provides a direct REST ingestion path.

These checks support component-level and local integration claims. They are not evidence of real-world seismic accuracy, hardware compatibility, optimal sensor counts, tsunami forecast skill, or ML severity performance.

## Recommended Claims for a Presentation

**Well supported:** “We built a Unity earthquake simulation in which a shared shaking model drives virtual seismic readings and building response. Those readings pass through per-station STA/LTA detection, multi-station epicenter estimation, and an MQTT event interface.”

**Supported with qualification:** “The system defines a mixed sensor data model and includes live seismic and simplified GNSS feeders; ocean-bottom, DART, and tide-gauge simulation feeds remain future work.”

**Do not claim as completed:** “The project optimizes hardware count from detection performance,” “the backend has been proven unchanged with physical sensors,” or “the severity ML model was trained on physics-labeled data.” Those require implementation and validation not present in this workspace.
